# 与现有实现对比的方法

状态：草案。阶段划分见 [roadmap](roadmap.md)，目标与边界见 [charter](charter.md)。

TekesUI 的验收参照是 Swift 栈 TekesMetalTextKit（私有仓库，Metal + CoreText + TextKit）。本文规定：拿什么夹具、量什么指标、容差多大、哪些自动判定、哪些在 Gallery 里人工目测，以及这套对比的工具和夹具在公开仓库里怎么放（第 5 节）。

本文只定方法，不复制任何私有代码或夹具内容，也不实现对比工具。

## 1. 对照对象与夹具

以下名称已在 TekesMetalTextKit 中核实存在（2026-10-15）。"在 TekesMetalTextKit 中"指该私有仓库内的相对位置。

| 名称 | 是什么 | 核实结果 | 用于阶段 |
|---|---|---|---|
| `MetalTextView` | 静态文字渲染的对照对象 | 存在 | F1 |
| `MetalDocumentView` | 只读文档渲染的对照对象 | 存在 | F3 |
| `HarnessStubSentences` | 一组句子文本夹具，分 A、B 两半，测试按名字读取 | 存在 | F1 起 |
| `markdown-style.json` | Markdown 样式配置，只含与默认样式不同的键 | 存在 | F3 |
| diff 测试用例 | 以 `MetalDiffDocumentViewTests`、`DiffBandProbeTests` 为代表 | 存在；具体取哪些用例作夹具，待与用户确认 | F3 |
| Markdown 投影测试用例 | 以 `MetalMarkdownInlineProjectionTests`、`MetalMarkdownStructuredProjectionTests` 为代表 | 存在；具体取哪些用例作夹具，待与用户确认 | F3 |
| `HarnessStubProfiler`、`HarnessStubNativeProfileTests` | 已有的性能剖析入口，可参考其指标口径 | 存在 | F1 性能 |

注意："HarnessStubSentences 对齐"是 F1 的验收口径：同一段文字、同一宽度、同一字体、同一 backing scale 下，两边排版结果一致。

TekesUI 自己也应另写一套可公开的原创夹具（中英混排、长段落、CJK 标点避头尾、emoji、组合字符、RTL 片段、代码块、表格、diff），与私有夹具并行，见第 5 节。

## 2. 对比指标

### 2.1 带容差的像素差异

做法：两边在相同条件（字体、字号、行高、宽度、前景/背景色、backing scale）下渲染到同尺寸位图，逐像素比较。

- 分辨率：1x 与 2x 分别比较，各自独立设门槛，不互相换算。3x 暂不比。
- 为什么要容差：参照侧走 CoreText 光栅化，含系统的字体平滑与亚像素定位；TekesUI 的光栅化器（字形来自系统字体、自己的 atlas）不保证逐位相同。容差要吸收的是抗锯齿灰度差，不是排版位置差。
- 建议判定（初值，F1 实测后修订）：
  1. 单像素通道差 ≤ 一个阈值（建议起点 24/255）的不计入差异；
  2. 超阈值像素占文字包围盒内像素的比例 ≤ 0.5%（1x）/ 0.3%（2x）；
  3. 不允许出现连续的"整字形缺失或整行偏移"：对差异图做连通域，任何面积超过一个字形的连通差异直接判失败，不看比例。
- 对齐方式：先用第 2.2 节的排版数据判定位置，再比像素；像素比较前不做自动平移对齐，位置偏移本身就是失败。
- 输出：差异热图 + 三个数字（超阈值比例、最大连通域面积、最大单像素差），放进对比报告。
- 生效阶段：F1 起对静态文字；F3 起对文档；F5 起对选区、caret、marked text 下划线。

### 2.2 排版数值

从两边各导出同一格式的结构化数据，逐项比较。这比像素稳定，应作为第一道门禁，像素比较是第二道。

| 项目 | 怎么量 | 建议门槛 | 阶段 |
|---|---|---|---|
| 断行位置 | 每个段落的行起止字符偏移（UTF-16 偏移或 grapheme 索引，导出格式里写明） | 完全一致，差一个字符即失败 | F1 |
| 行高与行基线 | 每行的 ascent、descent、leading、基线 y | 1x 下 ≤ 0.5pt，2x 下 ≤ 0.25pt（等价于 ≤ 半个设备像素） | F1 |
| 行宽 | 每行的排版宽度（含尾部空白与不含各一个） | ≤ 0.5pt | F1 |
| 字形位置 | 每个字形的 glyph id 与原点 (x, y) | glyph id 一致；原点 ≤ 0.25pt | F1 |
| caret 矩形 | 每个插入点索引对应的 caret 矩形（含双向文本的两个候选位置） | ≤ 0.5pt | F5 |
| 选区矩形 | 给定范围的选区矩形集合 | 矩形数一致，每个 ≤ 0.5pt | F3（只读选区）、F5 |
| 块级几何 | 文档中每个块（段落、标题、代码块、表格、diff 行）的 frame | ≤ 0.5pt | F3 |
| 内容总高度 | 给定宽度下的总高度 | ≤ 1pt | F3 |

门槛是起点，不是教条：若某项差异经确认来自参照实现自身的已知怪癖，应在对比报告里登记为"已知差异"并附理由，而不是悄悄放宽门槛。已知差异清单随仓库维护。

### 2.3 性能

在固定硬件（记录机型、系统版本、显示器刷新率）上量，每项至少跑 5 次取中位数，并记录最差值。

| 指标 | 怎么量 | 建议门槛 | 阶段 |
|---|---|---|---|
| 空闲 CPU | 内容静止、无动画、窗口可见 60 秒，取进程 CPU 占比 | 0（以采样器读数为准，允许 < 0.1% 的采样噪声）；不得有定时器空转或持续 redraw | F1 起，每阶段回归 |
| 滚动帧时间 | 在 120Hz 显示器上匀速滚动大文档，记录每帧 CPU 与 GPU 耗时 | p99 ≤ 8.3ms；不得有连续掉帧；不劣于参照实现 | F1（静态长文）、F3 |
| 打字延迟 | 按键事件时间戳到对应帧呈现的时间 | p95 ≤ 参照实现 + 1 帧；绝对值另设目标，F5 实测后定 | F5 |
| atlas 内存 | 加载夹具并滚动后的字形 atlas 占用字节数与页数 | 不超过参照实现的 1.25 倍（初值）；滚动前后不无界增长 | F1 起 |
| 冷启动到首帧 | 进程启动到夹具首次呈现 | 只记录趋势，暂不设门槛 | F1 |

"不劣于参照实现"指同一夹具、同一机器上的相对比较，参照侧数据由对比工具现场测，不依赖历史数字。

### 2.4 输入法验收矩阵（F5）

自动化不了的部分居多，由人工在 Gallery 的编辑页执行，结果记录在发版前的验收表里。通过判据通用约定：marked text 的下划线、候选窗位置、最终上屏文本、撤销行为都正确，且不出现重复上屏、丢字、光标跳动。

| 输入法 | 场景 | 通过判据 |
|---|---|---|
| 系统拼音 | 连续输入整句，候选翻页、数字选词、空格上屏 | marked text 样式正确；上屏文本与输入一致；回车提交英文原文 |
| 系统拼音 | 在已有文字中间插入 | 光标之后的文字位置随 marked text 增长实时重排；上屏后 caret 在新文字之后 |
| 系统拼音 | 换行折返处输入 | 候选窗锚定在 marked text 当前行，不遮挡正在输入的行 |
| 系统拼音 | 选区存在时开始输入 | 选区被替换；取消输入（Esc）后恢复原文或按系统行为一致 |
| 搜狗输入法 | 连续输入整句、联想词、自定义短语 | 同系统拼音；联想上屏后不重复 |
| 搜狗输入法 | 候选窗在页面底部附近 | 候选窗自动翻到 caret 上方，位置跟随 caret 矩形 |
| 微信输入法 | 连续输入整句、emoji 候选 | 同系统拼音；emoji 作为一个 grapheme 正确计数 |
| 微信输入法 | 快速连续输入与删除 | 无丢字、无残留 marked text |
| 听写 | 开启听写、说一整句话 | 听写过程中的临时文本以 marked text 显示；结束后定稿；撤销一次撤回整段听写 |
| 听写 | 听写中点击别处 | 临时文本被提交或取消，行为与参照实现一致，无残留 |
| 重新转换（reconversion） | 选中已上屏的词，触发重新转换 | 输入法拿到正确的选中范围与周边文本；替换后范围正确 |
| 重新转换 | 选区跨行、含 emoji、含组合字符 | 范围单位（UTF-16 / grapheme）正确，不错位 |
| 候选窗跟随滚动 | marked text 存在时滚动文档（滚轮、触控板、键盘） | 候选窗随 caret 矩形移动；caret 滚出可视区时候选窗行为与参照实现一致（贴边或隐藏），不停在屏幕旧位置 |
| 候选窗跟随滚动 | marked text 存在时窗口缩放、文档重排 | 候选窗位置在重排后更新 |
| 通用 | 双向文本、竖排（若支持）、全角半角切换 | 与参照实现一致；不支持的明确标注 |

后续的 Windows（TSF）与 Linux（IBus / Fcitx）按同一矩阵另列各自输入法，不在本文展开。

### 2.5 VoiceOver 清单（F6）

人工执行，每项记录通过 / 失败 / 与参照实现的差异。

- 静态文字：VO 光标逐字、逐词、逐行、逐段读取，内容与可视顺序一致。
- 文档结构：标题层级、列表、表格（行列数与表头）、代码块、链接、图片替代文本正确报出角色。
- 链接与按钮：可以用 VO 激活；焦点轮廓与 VO 光标位置一致。
- 选区：VO 报告选中文本；用 VO 命令移动选区后可视选区同步。
- 编辑：输入时 VO 朗读输入字符；删除时朗读被删字符；marked text 阶段的朗读不重复。
- caret 与行：VO 按行朗读时 caret 位置与朗读内容一致；滚动时 VO 光标可见区域跟随。
- 焦点：Tab / 逃逸快捷键能到达所有可交互元素；焦点离开时 VO 无残留。
- 动态内容：内容追加（流式）时 VO 不被打断、不重复朗读整段。
- 增强对比度与减弱动态效果：开启后 VO 工作正常，且视觉退化行为符合设计词汇。
- Gallery 本身：组件页的控件有名字、角色、状态；夹具说明文字可读。

## 3. 自动对比与人工目测的分工

| 方面 | 自动对比 | Gallery 人工目测 |
|---|---|---|
| 断行、行高、字形位置、caret、选区、块级几何 | 是（第 2.2 节，作为门禁） | 抽查 |
| 带容差像素差异 | 是（第 2.1 节，门禁） | 看热图与并排图，判断差异是否"可接受地不同" |
| 空闲 CPU、帧时间、atlas 内存 | 是（第 2.3 节，采样器） | 滚动手感、是否有肉眼可见的卡顿 |
| 打字延迟 | 部分（事件到呈现的时间戳） | 手感 |
| 输入法 | 否 | 是（第 2.4 节矩阵） |
| VoiceOver | 否 | 是（第 2.5 节清单） |
| hover / pressed / disabled / focus | 否（可截图回归，但是否"对"需要人看） | 是 |
| light / dark / increase contrast | 像素与对比度数值可自动 | 是，逐页看 |
| 整体观感、间距节奏 | 否 | 是 |

Gallery 里每个有参照对象的组件页，应并排展示：TekesUI 实时渲染、参照渲染图、差异热图。参照图是固定夹具、固定布局下预先生成的静态图，页面上标明生成它的参照实现版本和日期；Gallery 本身不依赖私有仓库在线。

### 3.1 目测时的窗口摆放约定

Gallery 以及验收中打开的任何窗口（包括自动化或子任务打开的）都按下面摆放，让每次目测时的显示条件一致：

1. 有外接显示器时，放到外接显示器上验证。只有需要 120Hz 刷新率的项目（例如 F1 的 120Hz 门槛、滚动帧时间），才放到内建显示器上做。
2. 没有外接显示器时，如果这项测试和窗口尺寸无关，窗口放在内建显示器的右半屏。
3. 和窗口尺寸相关的测试（如断行宽度、窗口缩放、候选窗定位）按夹具规定的尺寸摆放，不受第 2 条限制。

验收记录里注明用的是哪块显示器、刷新率和 backing scale。

## 4. 对比数据的交换格式

为了让对比工具与 TekesUI 解耦，仓库只定义"导出格式"，不依赖工具实现语言：

- 位图：PNG，文件名含夹具名、宽度、backing scale、外观（light/dark/ic）。
- 排版数据：JSON，字段至少包含上表 2.2 的各项，附带夹具名、字体名与字号、宽度、scale、导出方版本标识。
- 性能数据：JSON，含机型、系统版本、刷新率、各指标的原始样本与统计。
- 版本标识：参照侧记录它所依据的 TekesMetalTextKit 提交；TekesUI 侧记录自己的提交。

具体 schema 随 F1 一起落地，放在本仓库，不属于私有资产。

## 5. 公开仓库的注意点

已决定（2026-10-15）：采用方案 C 加原创夹具。日常门禁用 TekesUI 自己写的原创、可公开夹具及其黄金文件（参照位图加排版数值 JSON），公开 CI 自动比对；与私有夹具的效果对比在私有伴随仓库 TekesUI-compare 里跑，作为发版前关口。私有夹具的源文、对比工具和私有夹具的参照图都不进公开仓库。方案 B 只在 F1 之前作为临时起步手段。以下 A/B/C 三个方案保留为决策依据。

TekesMetalTextKit 与 Tekes 是私有仓库，TekesUI 是 MIT 公开仓库。两类东西不应直接放进公开仓库：

1. 对比工具：一个 pin 住 TekesMetalTextKit 某个提交的 Swift compare 工具（依赖私有源码）。
2. 从私有仓库复制来的夹具（句子文本、Markdown 样式配置、diff 与投影用例的内容）。

另外，从夹具渲染出的参照图本身包含夹具文字，等同于公开夹具内容的一部分。

### 方案 A：私有伴随仓库 TekesUI-compare

- 做法：新建私有仓库 TekesUI-compare，放 Swift compare 工具（pin 住 TekesMetalTextKit 提交）、夹具副本、参照图、对比报告。公开仓库只保留第 4 节的导出格式定义和 TekesUI 侧的导出器。对比时两个仓库并排检出，由伴随仓库驱动。
- 优点：工具与夹具的版权、私有性问题一次隔离；对比可以做到完整，包括像素与性能；pin 提交保证可复现。
- 代价：多维护一个仓库；外部贡献者无法复现对比，只能看公开的原创夹具上的结果；两个仓库的版本要同步。
- 对 CI 的影响：公开仓库的 CI 只能跑单元测试、原创夹具上的自测和导出格式校验；完整对比必须在能访问私有仓库的环境（本机或私有 CI）里跑，结果以报告形式回填。PR 门禁里不含完整对比，需要约定"发版前必须跑一次完整对比"。

### 方案 B：本地路径引用、不提交

- 做法：对比脚本通过环境变量，或被 .gitignore 的本地配置，指向本机的 TekesMetalTextKit 检出；工具与夹具都不进任何新仓库。公开仓库里只放"如何配置"的说明和导出格式。
- 优点：最轻量；不新增仓库；不存在误公开私有内容的路径（只要忽略规则正确）。
- 代价：可复现性弱，依赖开发者本机状态；参照实现版本靠约定而非 pin；参照图无处沉淀，Gallery 并排展示需要每次本地生成；换机器、换人就断。
- 对 CI 的影响：公开 CI 完全不涉及对比，只跑公开部分；对比是纯本地的人工流程，没有自动门禁，无法在 PR 上留证据。

### 方案 C：只公开参照渲染图与排版数值导出

- 做法：对比在私有环境里做，产物里的参照位图和排版数值 JSON 提交进公开仓库，作为"黄金文件"，TekesUI 的测试直接与黄金文件比较；夹具源文与工具不公开。
- 优点：公开 CI 就能做完整的自动对比（像素与排版数值），贡献者可复现；Gallery 的并排参照图有稳定来源。
- 代价：必须先确认渲染图里的文字内容可以公开（夹具文本是否原创、是否含第三方文字、是否含内部信息）；黄金文件更新要经过私有环境，更新流程有摩擦；位图体积会增长，需要约定存储方式（例如限定夹具数量与分辨率，必要时用 Git LFS）；参照图公开后，夹具文字事实上已公开。
- 对 CI 的影响：公开 CI 可以做门禁；黄金文件更新是一次受控的人工操作。

### 并行的原创夹具

无论选哪个方案，TekesUI 都应另写一套原创、可公开的夹具（并附明确的版权声明与 MIT 许可），覆盖与私有夹具相同的类别。它的作用是：让公开 CI 和外部贡献者始终有可用的回归夹具；方案 C 里，也可以只公开原创夹具的参照图，把私有夹具的参照图留在私有环境。

### 决定

采用 C 与原创夹具的组合，私有夹具的对比以 A 的形式在私有环境里跑：

- 日常门禁靠公开仓库里的原创夹具及其黄金文件，CI 自动跑、贡献者可复现；
- 与私有夹具的"效果对比"（本项目的核心验收）在私有伴随仓库 TekesUI-compare 里做，作为发版前关口；
- B 只作为最低成本的起步方式，F1 之前可以先用，不长期停留，因为它留不下证据。

理由：公开仓库需要自己能跑的回归，同时不能为此泄露私有夹具；两者用不同夹具、不同仓库分开，边界最清楚。该组合的代价是要维护 TekesUI-compare，并编写原创夹具，这两项成本已被接受。私有夹具的源文、对比工具和私有夹具的参照图，不提交进本仓库。
