# Window toolbar focus and input ownership

Root cause: each toolbar already had a real ContentHost and ToolbarControl, but the window sent ordinary keyboard input only to the currently selected Panel toolbar. Navigation and visibility contributions never entered the window Tab route; independent hosts could retain separate focus. Pointer capture was also split across visibility flags, navigation flags and a Panel-only owner, with different bubbling behavior.

## Repair and responsibilities

The Window host now retains one logical ToolbarTarget. It does not duplicate Button, Menu, command or roving state. Existing `ContentHost::focus_targets`, `focus`, `event` and cancellation continue to own group focus, disabled actions, Space/Enter, group arrows/Home/End and overflow. The Window only orders the existing groups by current visible layout: leading visibility, navigation, visible Panels in slot order, trailing visibility. Disabled/empty/hidden groups are skipped. Each toolbar remains one Tab stop; original left/right navigation selects actions inside that group.

Mouse focus and keyboard focus share that owner. The original ContentHosts are blurred/cancelled when ownership moves. A Tab during an old Space press cancels it before selecting the next group. Escape cancels an arm and retains a valid keyboard focus. System deactivation cancels pending input and removes active host focus; reactivation restores the still-valid logical owner, never an old activation arm. Hidden/disabled/removed owners are reconciled against the actual current component focus capability. Stable module ownership survives slot reordering and duplicate command IDs across modules remain isolated.

Toolbar pointer capture now uses the same typed owner rather than three independent capture flags. Existing event-bubbling results from visibility, navigation and Panel toolbars all reach the same eligible native titlebar drag handoff; old component input is cancelled first. An open toolbar Menu gets Tab and outside pointer events before any other toolbar, so an outside click closes it without activating a visibility button behind it. Navigation transaction input gates module actions as well as content input; stale geometry remains governed by original Toolbar descriptors and Panel command checks.

This is Window layout/input coordination, not a new framework-wide focus manager. The original ToolbarControls, ContentHosts and state machines remain. The former Host-local convenience capture flags/method are removed. Existing66pt native allocation/26pt control center,14pt artwork,20pt chrome, original hit areas, noSwap behavior and sidebar motion are retained.

## Applicable scope and exceptions

Applies to original AppHost-owned module, navigation and visibility toolbar contributions. Remote V1 content still does not support remote keyboard/IME/AX; this repair does not pretend to tab into remote editors. Generic caller Content toolbar groups/registry and per-action native AX remain separate architecture work. Standard original inline Toolbar and other component families have no source changes in this phase. User-deferred VoiceOver hearing remains deferred. OS/system shortcuts retain their modifier routing; modified system Tab is not converted into ordinary window traversal.

The repair keeps the one existing logical owner during transient busy, animation or a pending current viewport, while cancelling/blurred original ContentHost input. Tab uses the full visual group order to skip the blocked owner rather than restarting from the first group. Permanent hide/disable/failure still removes an invalid owner. Modified system Tab does not restyle or traverse a local group. Unavailable toolbar controls reject their actions but can offer unhandled chrome pointer input to AppKit.

This prevents an old Space arm firing after a new frame. Two real-Host regression cases cover pending-viewport restoration and the actual height-only Panel geometry path.
