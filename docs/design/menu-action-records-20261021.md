# Issue 36 — original menu delivery records (first implementation stage)

The root cause is a public component/action contract gap. MenuContent reused ButtonContent's trigger activation response, so opening could enter the generic action queue even though no menu command had been selected. A subsequent read of the mutable `selected` field cannot reconstruct two selections drained together. This is shared Menu behavior, not an AgentKit preference-state defect or a new design token requirement.

The existing action delivery queue now optionally carries owned data, captured synchronously from the originating component. `ContentActionRecord` retains the existing `ContentAction` plus the original opaque mount identity and optional `ContentActionPayload`. `ContentHost::drain_action_records` and `drain_actions` consume the same once-only queue; the legacy `ContentAction` stays Copy and its fields remain unchanged. Other original components default to no payload; wrappers delegating an original component's actions must also forward `Component::action_payload` when it has data. No callback runs during focus or paint.

MenuContent binds optional unique nonempty flat stable values with `set_values`. Each captured MenuSelection exposes the selected index, original label, model revision and optional stable value path via accessors. Existing positional callers can map `(model_revision, index)` to their own snapshot; binding values avoids polling mutable labels or selection entirely. Business option enums, preference revision and effects remain owned by the consumer, matching ClientKit's representedObject values for Sort/Group. The SDK does not import that domain model.

Opening by the original trigger or AX parent action does not emit a selection. Keyboard, pointer and AX item activations capture through the same original MenuView. Updating stable bindings closes and clears the old popup and held input through the existing runtime. Unchanged binding is a no-op; invalid binding rejects atomically. Direct legacy label mutation invalidates its revision and semantic parts until reconciliation, revokes old geometry and discards old positional value bindings before another item can activate. Queued already-captured selections survive later model changes; undrained selections are discarded on unmount/remount by the existing Content mount guard.

The common locations are composition/actions.rs (existing queue), composition.rs (default payload hook and exports), composition/adapters.rs (original MenuContent) and crate-private declaration storage/model replacement inside the existing MenuView in composite.rs. The original public MenuContent struct fields remain intact, including legacy external struct literals; the extra state is lazily initialized for those callers. The runtime replacement preserves existing window/motion configuration and cancels old held/scroll state. No new menu engine, rendering framework, editor, token or consumer-side hover control is introduced. Current source snapshots are retained under design/reviews/menu-selection-event-20261021/before.

This first stage establishes event capture for existing flat menus. Issue36 is **partially complete**: nested item/submenu/separator declarations, checked versus active-item semantics, per-item availability, original compact/compound trigger integration, stale popup-generation handling, full edge/clipping and final native/GPU/AX/consumer experience acceptance remain to be implemented and verified on a fixed final input. Flat menus are not a substitute for the requested Sort/Group submenus. No private packet or freeze recommendation is issued for this intermediate stage.

The second public consumer imports only public controls APIs. Its tests cover delayed A/B consumption after mutable selection and value-model changes, source-correct pointer/keyboard/AX selection, no selection on open/focus/paint/dismissal, held-pointer cancellation on binding replacement, invalid/idempotent bindings, direct label reorder before paint, and unmount/remount. These are API/runtime checks, not physical input or VoiceOver hearing. Source-bound current tests, strict Clippy, native/GPU and Gold7 evidence must remain separate; no whole-component maturity promotion, performance measurement or Git publication is implied.
