# F1 对比记录：TekesUI 与 TekesMetalTextKit

日期：2026-10-15。机器：Mac16,1（Apple M4），macOS 26.6.2（25G83），系统语言 `en-JP, ja-JP`。TekesUI 侧是 `tekes-ui-text` 的 CoreText 排版、atlas、`tekes-ui-render` 的离屏渲染；参照侧是私有伴随仓库 TekesUI-compare 用 TekesMetalTextKit 的 `MetalTextShaper.shape` 和真实 Metal 字形管线生成的排版导出与位图。参照数据是私有资产，本文只记命令、数字和描述。已知差异清单见 [../known-differences.md](../known-differences.md)。

## 运行

```bash
cargo run --release -p tekes-ui-compare -- \
  --fixtures fixtures/text \
  --reference <TekesUI-compare 检出>/reference \
  --out <临时目录或私有目录> \
  [--only 夹具名,夹具名] [--width 700,500] [--scale 1,2] [--no-images]
```

- 输出：`<out>/report.json`（`tekesui-compare-report/0`：机器、系统语言、两侧提交、夹具哈希、逐用例数值）、`<out>/report.md`（摘要表）、`<out>/<夹具>/` 下我们的排版导出、我们的渲染图和差异热图。`--out` 里有参照渲染的衍生图，不要放进公开仓库。
- 退出码：全部通过 0，有失败 1，参数或环境错误 2。
- 条件与参照一致：排版原点 (0, 0)，无内边距、无竖直偏移、无 backing 相位；画布是 `宽度 × ceil(总高度) × scale`；文本是夹具文件的原样内容，包括末尾的换行（所以多一个空行）；浅色前景 (0,0,0) 在 (255,255,255) 上，深色 (230,230,230) 在 (30,30,30) 上，读自 `reference/appearances.json`。
- `--origin-offset x,y` 只用于反向校验（把我们这一侧挪开，确认比较会失败），正式对比不要用。
- 自测不依赖私有数据：`cargo test -p tekes-ui-compare` 自己生成参照（排版导出加逐字形 `CTFontDrawGlyphs` 对照图），验证未改动时通过、断行被改时排版门禁失败、位图错位时像素门禁失败、缺文件时报错而不是 panic。

## 为什么没有需要修的东西，以及这个结论的限度

- 两侧用的是同一套系统调用：CoreText 的 `CTTypesetter` 断行和回退、`CTFontDrawGlyphs` 逐字形画进 BGRA8 预乘位图、整数像素原点、sRGB 编码空间里的预乘 alpha 混合。我在写 tekes-ui-text 时按调研笔记逐项实现，上一轮用 CoreText 直绘对照图验证过 atlas 路径；这一轮在真正的参照上得到同样的结果。
- 彩色 emoji、组合字符叠加（字形 y 与基线不同）、阿拉伯文和希伯来文（RTL，字形 run 顺序）、天城文和泰文（连字簇）都在夹具里，同样逐位一致。参照侧提示的"部分字形 y ≠ baseline_y"在我们这边同样出现，数值相同。
- 深色外观（前景 230，背景 30）与浅色一样逐字节相同，说明颜色处理（前景色以 value/255 进着色器、目标是非 sRGB 格式、编码空间里混合）两侧一致。
- 限度：只在同一台机器、同一系统版本、同一语言列表下比较。汉字的回退字体由语言列表决定（见已知差异 KD-2），换一台语言设置不同的机器，glyph id 会变，两侧要在同一台机器上生成。1x 的数据来自离屏渲染的 scale=1，不是真正的 1x 显示器。
- 反向校验过比较的灵敏度：把我们这一侧的原点向右挪 0.5pt，1x、2x 都失败（超阈值 13% 到 18%）；向下挪 0.5pt，1x 因为取整到同一个像素而仍通过（预期），2x 失败；挪 1pt 全部失败。
