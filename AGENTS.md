# TekesUI delivery ownership

- The coordinator owns priorities, domain boundaries, shared-interface ownership, acceptance, and delivery. Only the coordinator or its explicitly designated single integration executor integrates or commits on local `main`, publishes delivery branches, merges PRs, and creates milestone tags; the coordinator retains priorities, domain boundaries, and acceptance decisions. Preserve every unrelated checkout, WIP, candidate, and failure artifact.
- Domain leads own complete, independently consumable batches: read the linked Issues' effective acceptance criteria, coordinate dependencies and subagents, review their changes, complete scoped compilation plus their unit tests and necessary integration tests, fix failures, and deliver an integrated source/test patch with evidence. Domain leads do not run whole-workspace regression or repository-wide CI for each candidate; compilation alone does not satisfy behavioral acceptance. Subagents deliver to their domain lead. Small tasks can remain with one agent.
- Use persistent domain chats with independently verifiable deliverables. There is no fixed four-implementer cap: add domains when ownership and acceptance are independent and shared resources permit useful work. Domain chats use preset B (lead gpt-6.1-sol/medium; advisor gpt-6-astra/medium; worker and default subagent gpt-6-luna/high; scout gpt-6-luna/low; computer_use gpt-6.1-terra/medium). Reduce new implementation when integration or verification is the bottleneck. Assign one writer to each shared interface/file or explicitly disjoint hunks before editing; serialize conflicts through the coordinator. Never overwrite another owner's work.
- Candidates stay in isolated source workspaces. Stage only explicitly accepted files or hunks; never use `git add .`, import whole directories, recursively format, clean caches, or remove worktrees as part of delivery.
- Deliver in rolling independent batches: freeze each completed candidate and its exact evidence before continuing the next confirmed gap in the owned Issue. Do not silently modify a submitted batch, invent work to stay active, or let an unrelated waiting domain block a ready batch; preserve a separate commit/patch and input identity for the next batch. Only the designated integration executor switches MAIN sources and allocates shared build windows.

## Build and native resources

- Reuse the existing `scripts/tekesui_build.py` `build_lock()` and `environment()`, registered SSD routing, shared review cache, and existing GPU/native occupancy guards. Rust commands use `cargo +1.95.0 --locked --offline`. Confirm the SSD and actual source identity before execution; a path or commit label alone is not evidence of compiled inputs.
- The coordinator allocates build windows by source baseline. Within an allocated window, a domain lead may execute its necessary commands through the existing controlled entry point and must repair its failures; per-command message forwarding is unnecessary. Shared cache use remains serial. If an entry point only safely supports coordinator execution, retain that restriction and report its concrete limitation instead of introducing a scheduler.
- Do not create another target/cache, change storage registrations, clear caches, or alter source timestamps or flags to force recompilation. Do not kill or disturb other running tasks. Preserve source/program/configuration/dependency identities and raw results, including failures and checks that did not run. Do not reinstate the withdrawn source-closure proof gate.
- The coordinator schedules native windows and desktop input. A missing safe window blocks only the affected native checks; continue independent work. Programmatic events, AX queries, physical IME, VoiceOver, GPU pixels, and performance are separate evidence categories.

## Acceptance and delivery

- The coordinator collects complete, compatible domain batches and runs repository-wide CI once for the resulting integration batch. Group ready adjacent work before dispatching CI, while preserving commit history; do not wait for every project domain to finish or let an unrelated blocked capability delay a ready batch. Return CI failures to the owning domain with the exact failing inputs; repair and rerun affected checks, with another whole CI run only when required by changed shared inputs or the repository merge checks. Existing native, pixel and input acceptance criteria remain applicable within their actual scope.
- Reuse passing evidence when the relevant source, configuration, dependencies, environment, inputs, and contract are unchanged. A new commit SHA alone does not invalidate it. Collect independent failures for one baseline, repair them, then rerun only affected checks. The coordinator reviews actual diffs and primary artifacts and adds only necessary integration checks.
- Each formal handoff includes the Issue and scope, exact baseline and candidate commit/patch, allowed files/hunks, actual checks and reusable evidence, unverified items, dependencies, and concrete remaining gaps. A list of pending work or unprocessed small patches is not a completed batch.
- Silent handoff: do not send progress, acknowledgements, completion notices, repeated blockers, or CI-watch messages to the coordinator or other chats. Keep implementation/debugging logs in the domain chat. At a meaningful state transition, update only the owned current-summary section of the linked Issue, preserving other owners and original acceptance criteria. End the turn with one structured outcome: READY (complete tested batch), NEEDS_COORDINATION (specific interface/resource conflict), or NEEDS_DECISION (specific external/product decision). A completed chat turn is not evidence that its domain is complete; ordinary test failures remain the domain lead's responsibility.
- While actively coordinating, use completion/attention events through bounded multi-thread waits with cursors; do not schedule status polling, repeatedly read chats, or request routine progress. On a substantive completion event inspect the final handoff and primary artifacts. Do not claim persistent background monitoring after the coordinator turn ends. Keep one current summary per Issue and dynamic assignments in the coordination Issue, not this file.
- Prepare candidates and scoped tests before opening a PR. The coordinator opens or updates one PR for a complete compatible integration batch, not one PR per small fix or evidence supplement. Draft PRs currently also trigger full CI. Reuse existing passing PR checks; do not reopen or repush a verified tree merely to package it into a different batch.
- Deliver each accepted capability or complete dependency batch promptly: local main commit, delivery branch push, PR, required CI, normal merge to origin/main, and an annotated milestone checkpoint tag. Adjacent accepted dependent commits may share a PR while preserving their history. Do not squash, rebase, force-push, create formal Releases, or deploy.
- Partial deliveries use `Refs`; close an Issue only when every effective acceptance criterion is satisfied. Synchronize design changes with their existing design document and linked Issue. Advanced capabilities must not become a common prerequisite for ordinary local components. Preserve explicitly deferred and external-waiting work until its stated restoration condition is met.
